# Склад

Учебная модель складской системы на Python: категории, товары, остатки, заказы и доставка.
Это ядро будущего бэкенда: чистая бизнес-логика без веба и базы данных, которую позже можно подключить к API (например, FastAPI).

## Запуск

Нужен Python 3.11+.

```bash
uv run demo.py
# или
python demo.py
```

`demo.py` проходит полный сценарий: создаёт категории и товары, принимает поставку, оформляет заказы, передаёт курьеру, доставляет, отменяет и показывает, как обрабатываются ошибки.

## Структура

| Файл | Что внутри |
|---|---|
| `models.py` | сущности: `ItemCategory`, `WareHouseItem`, `OrderLine`, `Order`, доставка `Delivery` → `StandardDelivery`, `ExpressDelivery` |
| `enums.py` | статусы: `StockStatus` (наличие товара), `OrderStatus` (жизнь заказа) |
| `exception.py` | иерархия исключений с корнем `WareHouseError` |
| `mixins.py` | `JsonMixin` — добавляет метод `to_json()` |
| `warehouse.py` | `WareHouse` — сервис, который управляет складом; context manager `operation` |
| `demo.py` | сценарий использования |

## Возможности

- **Категории** создаёт администратор во время работы; товар можно создать только с существующей категорией.
- **Товары** создаются с количеством 0 и пополняются приёмкой (`receive`).
- **Статус наличия** (`IN_STOCK` / `OUT_OF_STOCK`) не хранится, а вычисляется из количества через `@property`, поэтому он никогда не расходится с остатком.
- **Заказ** принимает «бланк» вида `{id_товара: количество}` и выбранную доставку. Склад сам собирает позиции и фиксирует **цену на момент покупки**.
- **Резерв:** количество уменьшается сразу при оформлении, чтобы один товар не продали дважды.
- **Жизненный цикл заказа:**

  ```
  CREATED ──► SHIPPED ──► DELIVERED
     │           │
     └───────────┴──► CANCELLED   (товар возвращается на склад)
  ```

  Недопустимые переходы (например, отменить доставленный заказ) вызывают `InvalidStatusTransition`.
- **Доставка:** обычная (бесплатно, дольше) и экспресс (платно, быстрее). Итог заказа = товары + доставка.

## Где какое требование

| Требование | Реализация |
|---|---|
| Абстрактный класс (`abc.ABC`) + 2 реализации | `Delivery` с абстрактными `cost()` и `days()` → `StandardDelivery`, `ExpressDelivery` |
| Mixin | `JsonMixin` подмешан к `ItemCategory`, `WareHouseItem`, `Order` |
| `dataclass` для сущностей | `ItemCategory`, `WareHouseItem`, `OrderLine`, `Order` |
| `Enum` для статусов | `StockStatus`, `OrderStatus` |
| Своя иерархия исключений | `WareHouseError` → `CategoryAlreadyExists`, `CategoryNotFound`, `ItemAlreadyExists`, `ItemNotFound`, `InvalidQuantity`, `InvalidPrice`, `OrderNotFound`, `InvalidStatusTransition`, `NotEnoughStock` |
| Context manager | `operation(name)` через `@contextmanager`: логирует начало, конец и длительность операции, «конец» печатается даже при ошибке |

## Композиция вместо наследования

Правило, которым я руководствовался: наследование только там, где честно звучит «**является**» и у наследников **разное поведение**. Во всех остальных случаях — композиция («**имеет**»).

- **Товар имеет категорию**, а не наследуется от неё. Категории — это данные, которые администратор создаёт во время работы приложения; у разных категорий нет разного поведения, а товару может понадобиться сменить категорию. Если бы каждая категория была классом, новую категорию мог бы добавить только программист.
- **Заказ имеет позиции** (`list[OrderLine]`). Позиция — это связь «товар + количество + цена на момент покупки», а не разновидность товара или заказа.
- **Заказ имеет доставку** (`delivery: Delivery`), а не `ExpressOrder(Order)` / `StandardOrder(Order)`. Так способ доставки можно заменить, не создавая новый объект заказа, а новый вид доставки не требует новых классов заказов.
- **Склад имеет** словари категорий, товаров и заказов и управляет ими. Склад не является коллекцией — он сервис над ней.

Наследование использовано в одном месте — для доставки: `StandardDelivery` и `ExpressDelivery` действительно **являются** доставками и по-разному отвечают на `cost()` и `days()`. Заказ вызывает эти методы, не зная, какая доставка внутри (полиморфизм). Чтобы добавить, например, самовывоз, достаточно написать новый класс-наследник `Delivery` — остальной код не меняется.

## Решения, которые стоит отметить

- **Сначала проверки, потом изменения.** В `place_order` два цикла: первый только проверяет все позиции, второй списывает. Если на любой позиции ошибка, склад остаётся нетронутым.
- **Склад принимает данные, а объекты собирает сам** (`create_item(id, title, category_id, price)`, `place_order(id, {item_id: qty}, delivery)`). Так проще подключить веб-API: от клиента приходят просто числа.
- **Поиск через помощники** `_get_item`, `_get_category`, `_get_order` превращает технический `KeyError` в понятные `...NotFound` в одном месте.

## Что можно улучшить

- Красивое JSON-представление доставки (сейчас это строка с именем объекта).
- Транзакции: откат нескольких операций целиком при ошибке.
- Весовые товары (продажа 2,5 кг) как ещё один пример полиморфизма.
- Тесты на `pytest` вместо `demo.py`.
- Хранение в базе данных (SQLite / PostgreSQL) и веб-API на FastAPI.
